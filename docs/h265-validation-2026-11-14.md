# FilmCraft H.265 독립 검증 — 2026-11-14

## 범위

기준 소스는 ArtCraft PR #6의 `0c712e78b42ff191164a8b4902ae6a078feebae9`다. Apple M1(8 CPU), RAM 16GiB, Rust/Cargo 1.99.1, 외부 FFmpeg/ffprobe 9.0.2에서 직접 실행했다. 원격 Windows/NVIDIA·Linux의 결과가 아니다.

제품 인코더·디코더 구현을 변경하지 않았다. 테스트 2개를 추가하고, 기존 속도 테스트의 슬라이스 수가 실제 출력 코드와 달랐던 부분을 수정했다. main에 동시에 병합된 오프라인 큐 PR #7은 그대로 보존했고 이 H.265 커밋에서는 수정하지 않았다. 로컬 미커밋 리뷰 수정은 반영 대상이 아니며, 배포·Netlify 접근 설정도 변경하지 않았다.

[데스크톱 앱 실제 내보내기](#데스크톱-앱-실제-내보내기--2026-11-14) 절만은 이후 main `02cad734`(위 기준 소스 뒤에 PR #7·#8과 이 문서의 검증 커밋이 더해졌고, `filmcraft/`에서는 테스트·문서만 바뀌어 제품 H.265 코드는 같음)의 로컬 릴리스 빌드로 따로 실행했다. 이 절은 cargo 테스트가 아니라 앱 화면에서 내보낸 결과다.

## libkvazaar 환경과 fuzz

시스템 FFmpeg에 libkvazaar가 없어 중단됐던 검사를 별도 오라클 환경에서 다시 실행했다. 새 fixture 폴더에서 5개 seed를 생성해 전체 truncation/header-bit 변이 검사 및 seed당 무작위 400회를 실행했다. `FILMCRAFT_REQUIRE_ORACLES=1`에서 스킵 없이 **libtest 1개 통과·실패 0·ignored 0, 31.78초**다. 5개 seed나 무작위 2000회를 각각 별도의 Rust 테스트 개수로 부풀리지 않는다.

원래 fuzz 소스와 단언·600초 deadline은 변경하지 않았다. [입력·실행 영수증](h265-fuzz-verification-2026-11-14.json)에 외부 실행 파일·원본 로그와 5개 seed의 SHA-256을 기록했다.

```sh
FILMCRAFT_FFMPEG=/absolute/hevc-test-oracle/bin/ffmpeg \
FILMCRAFT_FFPROBE=/absolute/hevc-test-oracle/bin/ffprobe \
FILMCRAFT_FIXTURES_DIR=/absolute/new-fuzz-fixtures \
FILMCRAFT_REQUIRE_ORACLES=1 FILMCRAFT_FUZZ_ITERS=400 FILMCRAFT_FUZZ_SEED=20771 \
cargo test --locked --release -p filmcraft-hevc --test fuzz_hostile -- --nocapture --test-threads=1
```

외부 오라클은 제품 코드에 복사·링크·번들하지 않는다. [FFmpeg 공식 libkvazaar 문서](https://ffmpeg.org/ffmpeg-codecs.html#libkvazaar)에 따라 별도 테스트 실행 파일을 준비했다. 시스템 FFmpeg는 교체하지 않는다.

### 테스트 전용 FFmpeg 구성

macOS에서 `brew install kvazaar pkgconf x265`로 외부 빌드 의존성을 준비했다. 공식 FFmpeg 9.0.2 tarball의 SHA-256은 `8c3850283eb25fa026482078a04051e0be17347b09ef81a0849bec15a96e002e`였다. 소스는 외부 오라클 빌드에만 사용했으며 구현 코드를 제품으로 가져오지 않았다.

다음 구성으로 `make -j2`, `make install`을 실행했다. `wrapped_avframe`은 lavfi의 testsrc2 입력 처리에 필요하다. 첫 최소 구성에는 이 디코더가 빠져 fixture 생성이 실패했으며 이를 추가해 환경을 수정했다. `pkgconf`도 필요하다.

```sh
./configure --prefix=/absolute/hevc-test-oracle \
  --disable-everything --disable-autodetect --disable-doc --disable-debug \
  --enable-gpl --enable-libx265 --enable-libkvazaar --enable-ffmpeg --enable-ffprobe \
  --enable-encoder=libx265,libkvazaar,rawvideo,wrapped_avframe \
  --enable-decoder=hevc,rawvideo,wrapped_avframe \
  --enable-demuxer=hevc,rawvideo --enable-muxer=hevc,rawvideo,null \
  --enable-protocol=file,pipe --enable-indev=lavfi \
  --enable-filter=testsrc2,format,scale,null,buffer,buffersink \
  --enable-parser=hevc --enable-swscale \
  --extra-cflags=-I/opt/homebrew/include --extra-ldflags=-L/opt/homebrew/lib
make -j2
make install
```

이 실행 파일은 HEVC 검사에 필요한 최소 구성이다. 다른 코덱의 전체 workspace 검사에는 기존 외부 FFmpeg를 사용했다. 테스트 도구의 구성 차이와 실제 제품 코덱 실패를 구분한다.

| software-8k-sdr | 2 | 6.586 | 0 | 통과 |

software는 하드웨어 팩토리를 등록하기 전 실행한다. 기존 H.265 계약은 `HardwareEncoding::Off`여도 등록된 하드웨어를 먼저 시도하므로 Off만으로 소프트웨어 경로를 증명할 수 없다. 첫 검사에서 이 잘못된 가정을 발견해 독립 소프트웨어 조건으로 수정하고 재실행했다.

실패 주입은 초기화 오류를 반환하는 팩토리를 등록하고, 뒤의 실제 VideoToolbox 팩토리는 비정사각 픽셀 설정으로 거절하게 한다. 오류 팩토리 호출 1회, 하드웨어 프레임 0개, 소프트웨어 8프레임 PQ 정상 파일을 확인했다. 인코딩 도중 GPU/드라이버 장애나 전원 차단의 복구 시험은 아니다.

PQ 파일에는 1000nit mastering display와 CLL SEI가 있다. 현재 `ColorSignal::static_metadata()`의 MaxCLL/MaxFALL 기본값 `(0,0)`을 확인했으며 실제 콘텐츠의 최대 밝기를 측정했다는 뜻은 아니다. 외부 Annex-B 추출로 소프트웨어 4K·8K의 모든 프레임이 16개 슬라이스임도 확인했다.

4K 4프레임·8K 2프레임의 짧은 OceanSunset 합성 씬이며 전체 출력 시간에는 렌더링·변환·인코딩·컨테이너 생성이 포함된다. 시작 비용과 시스템 부하의 영향이 크므로 하드웨어/소프트웨어의 일반적인 속도 순위나 장편 성능으로 해석하지 않는다.

## 압축 품질

외부 FFmpeg의 testsrc2 합성 영상, 1280×720, 24fps, 120프레임(5초), 8비트 SDR. IDR 48, 6개 슬라이스, 평균 비트레이트·최대 1.5배 ceiling을 사용했다. encode-only 시간은 원본 생성·I/O·입력 준비를 제외한다.

| 목표 kbps | 실제 kbps | 밝기 PSNR dB | 전체 SSIM | encode-only fps |
| --- | --- | --- | --- | --- |
| 1000 | 1019.86 | 34.61 | 0.961116 | 18.97 |
| 2000 | 2032.83 | 38.32 | 0.979392 | 20.19 |
| 4000 | 4053.93 | 44.07 | 0.992249 | 15.01 |

외부 FFmpeg로 디코딩한 모든 샘플의 SHA-256이 각 인코더 reconstruction과 일치했다. 이는 재구성의 정확성이고, 손실 압축 원본과 무손실로 같다는 뜻이 아니다. 같은 입력의 외부 x265 medium 참조는 약 2.20Mbps에서 밝기 PSNR 43.51dB·전체 SSIM 0.99436이었다. 실제 비트레이트·스레딩·구현이 달라 엄밀한 동일 조건 비교는 아니지만, 이번 샘플에서 자체 인코더의 압축 효율 개선 여지는 확인됐다.

합성 영상 하나의 결과이므로 실사·그레인·고속 운동·다종 카메라 원본 전체의 품질을 대표하지 않는다. x265는 외부 참조 도구로만 사용했다.

| --- | --- | --- | --- |
| 1920×1080 8비트 | 30 | 9.22 | 3.25 |
| 3840×2160 10비트 | 8 | 10.21 | 0.78 |

## 데스크톱 앱 실제 내보내기 — 2026-11-14

main `02cad734`를 같은 Mac에서 로컬 릴리스 프로필로 빌드(`cargo build --release --locked -p filmcraft`, `CRAFT_FONTS_DIR` 없음)해 실행했다. 배포용 릴리스 패키지(craft-fonts 포함·서명)는 아니다. 사용자가 쓰는 내보내기 화면으로 데모 프로젝트의 Main Edit 시퀀스(1920×1080, 23.976fps, 26.777초)를 출력했다. 사용자 설정을 건드리지 않도록 새 임시 설정 폴더(`FILMCRAFT_DATA_DIR`)를 썼다.

조작 방식은 다음과 같다. 형식·파일 이름·위치·프레임 크기·픽셀 종횡비·범위·내보내기 버튼은 제어 채널의 화면 클릭과 입력(`ui.click`·`ui.key`·`ui.type`)으로 바꿨고, 내보내기 설정을 직접 주입(`ui.set`)하지 않았다. 시퀀스 색 관리 창만은 메뉴를 클릭하지 않고 제어 채널의 메뉴 명령(`ui.menu.invoke` `sequence.colorSettings`)으로 열었으며, 창 안의 색 공간 선택과 확인은 클릭했다. 실행 방법은 아래 [재현](#데스크톱-앱-내보내기)에 적었다.

| 출력 | 인코더 | 범위 | 프로필·색 | 프레임 | 소요 초 | 크기 | 영상 비트레이트 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1920×1080 SDR | VideoToolbox | 전체 26.777초 | Main, BT.709 | 642/642 | 39.8 | 9.4MB | 2.49Mbps |
| 3840×2160 SDR | VideoToolbox | 전체 26.777초 | Main, 레벨 5.0, BT.709 | 642/642 | 102.9 | 9.0MB | 2.36Mbps |

소요 시간은 렌더링(비디오 클립 7개, time_remap·lumetri·drop_shadow 효과)·인코딩·컨테이너 생성을 포함하며, 같은 Mac에서 사용자의 다른 FilmCraft 창과 다른 작업이 함께 돌던 상태에서 쟀다. 성능 비교나 앞 절 벤치마크와의 대조에 쓰지 않는다.

- 형식 목록에서 H.265 (HEVC)를 고르면 프로필은 "Main (8비트, HDR 시퀀스는 Main 10)", 인코더는 "가능하면 하드웨어, 아니면 소프트웨어"로 고정 표시된다. 시퀀스 색 관리를 Rec. 2100 PQ나 HLG로 바꾸자 프로필 표시가 "Main 10 (10비트, HDR)"로 바뀌었다.
- 화면에 인코더 선택은 없지만, VideoToolbox가 거절하는 설정(비정사각 픽셀·홀수 크기·2패스 VBR·CRF, `crates/platform/src/hardware_encode.rs`의 `config_for`)을 고르면 자체 인코더로 넘어간다. 픽셀 종횡비를 "HD Anamorphic 1080 (1.333)"으로 바꾼 두 출력은 설정 폴더의 `Logs/filmcraft.log`에 `hardware HEVC encoding declined: non-square pixels`가 기록됐고 자체 인코더가 만들었다.
- 인코더는 비트스트림으로도 구분했다. VideoToolbox 출력 5개는 SPS의 SAO가 켜져 있고 디블로킹이 꺼져 있지 않으며 모든 프레임이 슬라이스 1개다. 자체 인코더 출력 2개는 SAO가 꺼져 있고 PPS가 디블로킹을 끄며 모든 프레임이 슬라이스 9개(128행당 1개)다.
- 일곱 파일 모두 MP4/hvc1·AAC 48kHz 스테레오다. 외부 FFmpeg 9.0.2로 영상과 음성을 끝까지 디코딩해 오류 0건, 디코딩한 영상 프레임 수가 위 표와 같음을 확인했다.
- macOS AVFoundation(`AVAssetReader`)으로도 일곱 파일 모두 재생 가능(`isPlayable`)하고 모든 영상 프레임이 디코딩됐다. PQ·HLG 파일 3개는 HDR 영상(`containsHDRVideo`)으로 인식됐다. 픽셀 4:3 파일은 macOS 썸네일이 16:9로 그려졌다.
- PQ 파일 2개에는 1000nit mastering display가 있고, MaxCLL/MaxFALL은 앞 절과 같이 기본값 `(0,0)`이다.
- 화질은 일부만 눈으로 봤다. 각 파일의 3초 지점 macOS 썸네일(960×540, HDR은 macOS가 SDR로 바꿔 그림) 한 장씩과, ffmpeg로 뽑은 4K SDR 원본 크기 부분 2장·자체 인코더 1440×1080 원본 크기 부분 1장에서 깨짐은 보이지 않았다. 8K·HDR 파일은 원본 크기로 보지 않았다.
- VideoToolbox 출력의 비트레이트(1.49–6.37Mbps)는 목표 20Mbps·최대 30Mbps보다 크게 낮았다. FilmCraft는 VBR에서 목표를 `AverageBitRate`, 최대를 `DataRateLimits`로 그대로 넘기므로(`crates/platform/src/videotoolbox_encode.rs`), 덜 쓴 것은 VideoToolbox의 판단이다. 같은 내용을 자체 인코더로 내보낸 SDR은 18.48Mbps로 목표에 가까웠다. 비트가 필요한 영상에서는 VideoToolbox도 목표를 지켰다(아래 절).

### 복잡한 4K 영상의 VideoToolbox 비트레이트·화질

데모 프로젝트의 낮은 비트레이트가 영상이 단순한 탓인지 보려고, 외부 FFmpeg로 3840×2160·23.976fps·5초(119프레임) ProRes 422 시험 영상 2개를 만들었다. `testsrc2`에 시간 방향 균일 잡음을 더했고, 강도는 실사의 입자 잡음 정도(`alls=12`)와 압축이 거의 불가능한 수준(`alls=40`)이다. 같은 릴리스 빌드를 새 임시 설정 폴더로 띄우고, 영상 가져오기와 클립으로 시퀀스 만들기는 엔진 명령(`file.import`, `file.newSequenceFromClip`)으로, 내보내기는 앞 절과 같이 내보내기 화면 클릭과 입력으로 했다.

H.265는 기본 설정(VBR 1패스, 목표 20Mbps·최대 30Mbps)과 목표 50Mbps·최대 75Mbps로 내보냈다. 같은 시퀀스를 FilmCraft의 ProRes 422 HQ로도 내보내 기준으로 삼아, 디코딩·렌더링·색 변환 과정의 차이와 압축 손실을 나눴다. PSNR·SSIM은 외부 FFmpeg로 양쪽을 4:2:0 8비트로 바꿔 모든 프레임을 같은 순서로 비교했다.

| 영상 | 목표 | 실제 영상 비트레이트 | PSNR Y (원본 대비) | PSNR Y (FilmCraft ProRes HQ 대비) | SSIM (원본 대비) |
| --- | --- | --- | --- | --- | --- |
| 입자 잡음 | 20Mbps | 19.99Mbps | 42.79dB | 43.32dB | 0.9681 |
| 강한 잡음 | 20Mbps | 20.20Mbps | 34.78dB | 35.21dB | 0.7866 |
| 강한 잡음 | 50Mbps | 50.05Mbps | 35.38dB | 35.83dB | 0.8052 |
| FilmCraft ProRes 422 HQ (입자 / 강한 잡음) | — | 약 700Mbps | 53.58 / 51.38dB | — | 0.9967 / 0.9958 |

- 복잡한 영상에서는 VideoToolbox가 목표를 거의 정확히 썼고, 목표를 50Mbps로 올리자 그대로 따라갔다. 데모 프로젝트의 1.49–6.37Mbps는 영상이 단순해서 VideoToolbox가 비트를 덜 쓴 결과다.
- FilmCraft의 ProRes 422 HQ 출력은 원본과 51–54dB로, 디코딩·렌더링·색 변환이 정확했다. 그래서 H.265 출력의 원본 대비 손실은 대부분 압축 손실이다.
- 강한 잡음은 목표를 2.5배로 올려도 PSNR이 0.6dB만 올랐다. 같은 원본을 외부 x265(libx265 medium, 같은 목표·최대, `bufsize`=최대, 키프레임 48, 4:2:0 8비트)로 인코딩해도 아래처럼 0.7dB만 올랐다. 프레임마다 무작위로 바뀌는 잡음이 압축되지 않는 탓이고 VideoToolbox만의 한계는 아니다. 입자 잡음에서는 x265가 1.48dB 높았다(x265는 B프레임을 쓰고, FilmCraft는 VideoToolbox의 프레임 재배열을 끔).

| 영상 | 목표 | x265 실제 비트레이트 | x265 PSNR Y | x265 SSIM | VideoToolbox PSNR Y |
| --- | --- | --- | --- | --- | --- |
| 입자 잡음 | 20Mbps | 20.59Mbps | 44.27dB | 0.9707 | 42.79dB |
| 강한 잡음 | 20Mbps | 21.45Mbps | 35.07dB | 0.7888 | 34.78dB |
| 강한 잡음 | 50Mbps | 54.85Mbps | 35.78dB | 0.8110 | 35.38dB |

- 세 H.265 출력 모두 VideoToolbox가 만들었다. 설정 폴더 로그에 거절 기록이 없고, 비트스트림에서도 119개 프레임 모두 SAO가 켜져 있고 디블로킹이 꺼져 있지 않으며 슬라이스가 1개다(앞 절의 VideoToolbox 출력과 같음). 외부 FFmpeg 전체 디코딩 오류는 0건이다.
- 첫 측정에서는 원본 대비 PSNR이 약 24dB로 나왔다. 원인은 시험 영상 쪽이었다. FFmpeg가 RGB 합성 영상을 BT.601 행렬로 YUV로 바꾸면서 색 정보를 붙이지 않았고, FilmCraft는 색 정보가 없는 HD·4K를 관례대로 BT.709로 읽었다(차이 영상에서 색 띠마다 일정한 차이로 보임). BT.709로 변환하고 `colorspace`를 붙인 영상으로 다시 잰 값이 위 표다.
- 합성 잡음 영상 2개의 결과이며, 실제 카메라 원본의 디테일·움직임을 대표하지 않는다.

### 실사 4K 영상(Tears of Steel)의 비트레이트·화질 — 2026-11-16

실제 촬영 영상으로 같은 시험을 했다. 원본은 Blender Foundation의 단편 [Tears of Steel](https://mango.blender.org/)(CC BY 3.0, Sony F65로 찍은 실사에 VFX를 더함)의 4K 배포판 `tearsofsteel_4k.mov`다. [download.blender.org](https://download.blender.org/demo/movies/ToS/)에서 받은 ZIP의 크기가 목록과 바이트 단위로 같았다. 영상은 H.264 High, 3840×1714, 24fps, 73.2Mbps이고 색 정보가 없다. 카메라 RAW가 아니라 이미 압축된 배포판이므로, 그 압축 흔적이 원본에 포함돼 있다. 받은 영상과 잘라 낸 구간은 저장소에 넣지 않았다.

성격이 다른 세 구간을 10초(240프레임)씩 골랐다. 원본 H.264를 그대로 자르지 않고, 외부 FFmpeg로 디코딩해 ProRes 422 HQ(4:2:2 10비트)로 옮긴 구간을 시험 원본으로 썼다. 키프레임이 아닌 곳부터 디코딩하면 FFmpeg가 참조 프레임이 없다는 경고(`mmco: unref short failure`, `Missing reference picture`)를 냈기 때문이다. GOP 구조 자체는 조사하지 않았다. 원본에 색 정보가 없어서, 구간에는 HD·4K의 관례에 따라 BT.709·제한 범위(`-colorspace bt709 -color_range tv`)를 붙였다. 따라서 FilmCraft가 이 시험에서 읽은 것은 BT.709로 표시된 ProRes이고, FilmCraft 자체의 H.264 디코더와 색 정보가 없는 영상의 처리는 이 시험에 포함되지 않는다.

장면 전환은 외부 FFmpeg `scdet`(임계값 12)로 셌다.

- A(190–200초): 어두운 VFX 거리 → 인물 클로즈업. 장면 전환 1번(8.5초)
- B(280–290초): 운하 거리를 걷는 인물 → 실내 인물. 장면 전환 1번(9.54초)
- C(460–470초): 총격과 움직임 흐림이 큰 액션. 장면 전환 3번(1.79, 4.83, 8.33초)

앞 절과 같은 릴리스 빌드(`02cad734`)를 새 임시 설정 폴더로 띄우고, 같은 방식으로 가져와 내보냈다. H.265는 기본 설정(VBR 1패스, 목표 20Mbps·최대 30Mbps)이고, 기준 파일은 FilmCraft의 ProRes 422 HQ 출력이다. x265는 앞 절과 같은 설정(libx265 medium, 목표 20Mbps·최대 30Mbps, 키프레임 48)으로 같은 원본(ProRes 구간)을 인코딩했다. 아래 "원본"은 모두 이 ProRes 구간이다.

| 구간 | VideoToolbox 비트레이트 | PSNR Y / SSIM (원본 대비) | FilmCraft ProRes HQ (원본 대비) | x265 비트레이트 | x265 PSNR Y / SSIM |
| --- | --- | --- | --- | --- | --- |
| A | 20.02Mbps | 45.27dB / 0.9820 | 55.57dB / 0.9980 | 20.97Mbps | 46.09dB / 0.9843 |
| B | 19.99Mbps | 42.12dB / 0.9704 | 55.44dB / 0.9983 | 20.27Mbps | 42.31dB / 0.9718 |
| C | 20.01Mbps | 45.44dB / 0.9855 | 55.60dB / 0.9981 | 23.05Mbps | 46.79dB / 0.9880 |

- 실사에서도 VideoToolbox는 목표를 거의 정확히 썼다. 합성 잡음 영상과 같은 결과이고, 데모 프로젝트의 낮은 비트레이트가 영상이 단순한 탓이라는 결론과 맞는다.
- FilmCraft의 ProRes 422 HQ 출력은 원본(BT.709로 표시한 ProRes 구간)과 55.4–55.6dB로, 이 구간의 디코딩·렌더링·색 변환이 정확했다. 그래서 H.265의 원본 대비 손실은 대부분 압축 손실이다.
- VideoToolbox는 목표와 0.1% 안으로 맞았지만, x265는 세 구간 모두 목표보다 비트를 더 썼다(A 4.8%, B 1.4%, C 15% 많음). 비트레이트가 가장 비슷한 B에서 x265가 0.19dB 높았고, A의 0.82dB와 C의 1.35dB 차이에는 더 쓴 비트의 몫이 섞여 있다.
- 세 H.265 출력 모두 VideoToolbox가 만들었다. 거절 기록이 없고, 240개 프레임 모두 SAO가 켜져 있고 슬라이스가 1개다. 외부 FFmpeg 전체 디코딩 오류는 0건이다. 내보내기 시간은 H.265 10.9–12.9초, ProRes HQ 28.2–30.8초였다(다른 작업과 함께 잰 값).
- 화질은 B 구간 60번째 프레임 한 장만 원본 크기(960×540 부분)로 비교했다. 깨짐은 없었고, 벽돌 질감 같은 미세한 입자가 원본보다 조금 부드러워졌다. A·C와 다른 프레임은 원본 크기로 보지 않았다.

### 실사 H.264를 FilmCraft가 직접 읽기(Tears of Steel 1080p) — 2026-11-17

앞 절은 FFmpeg로 ProRes로 옮긴 구간을 썼으므로, FilmCraft가 H.264를 직접 디코딩하는 경로와 색 정보가 없는 영상의 처리는 확인하지 못했다. 이번에는 같은 영화의 1080p 배포판 `tears_of_steel_1080p.mov`(같은 [download.blender.org](https://download.blender.org/demo/movies/ToS/) 폴더)를 변환하지 않고 그대로 FilmCraft에 넣었다. 목록의 ZIP 크기는 583,774,281바이트이고, 압축을 푼 `.mov`는 583,774,083바이트였다(받은 ZIP의 바이트 크기는 따로 대조하지 않았다). 영상은 H.264 Main@4.0(CAVLC, 가중 P 예측, B프레임), 1920×800, 24fps, 영상 스트림 6.2Mbps(MP3 음성을 합친 파일 전체 6.4Mbps), 17,620프레임이고 색 정보가 없다. 키프레임 999개가 모두 IDR이고 약 18프레임 간격이다. 받은 영상은 저장소에 넣지 않았다.

macOS의 FilmCraft는 H.264를 VideoToolbox로 디코딩하고, VideoToolbox가 거절하거나 실패하면 자체 디코더(`crates/h264`)로 넘어간다. 두 경로를 따로 시험하려고 앞 절과 같은 릴리스 빌드(`02cad734`, H.264 디코딩 코드는 `7cf1de1e`까지 바뀌지 않음)를 새 임시 설정 폴더로 두 번 띄웠다. 어느 디코더가 썼는지는 `perf.stats`의 `decode.hardware`로 확인했다.

- 1회차: 하드웨어 디코딩 기본값(자동). VideoToolbox 1,484프레임, 자체 디코더 0프레임, 전환 0회.
- 2회차: 가져오기 전에 `playback.hardwareDecoding`을 `off`로 설정. 자체 디코더 1,498프레임, VideoToolbox 0프레임.

내보낸 프레임은 회차마다 6개 출력을 합쳐 1,440프레임이다. 디코딩한 프레임 수가 그보다 44·58프레임 많은 것은 구간 시작 앞의 키프레임부터 디코딩해야 하는 몫(구간마다 0·10·3프레임)과 화면 표시용 디코딩으로 보인다. 두 회차의 차이는 따로 조사하지 않았다. 디코더 판단에는 하드웨어와 자체 디코더 중 어느 쪽이 0인지만 썼다.

회차마다 `.mov`를 가져와 시퀀스를 만들고, 앞 절과 같은 위치에서 10초(240프레임)씩 사용자 정의 범위로 Apple ProRes 422 HQ와 H.265 기본 설정(VBR 1패스, 목표 20Mbps)으로 내보냈다. 기준은 외부 FFmpeg 9.0.2가 파일 처음부터 디코딩한 프레임 중 같은 번호의 240프레임(4560·6720·11040번부터)이다. 둘 다 yuv420p로 맞춰 프레임 번호로 짝지었고, 기준에는 FilmCraft가 읽는 대로 BT.709·제한 범위를 붙였다.

| 구간 | ProRes HQ PSNR Y / SSIM Y | 가장 낮은 프레임 | 첫 3프레임 | H.265 비트레이트 | H.265 PSNR Y / SSIM Y |
| --- | --- | --- | --- | --- | --- |
| A(190–200초) | 53.73dB / 0.9969 | 52.86dB | 53.19·53.37·53.34dB | 20.00Mbps | 49.66dB / 0.9944 |
| B(280–290초) | 52.59dB / 0.9971 | 51.43dB | 53.11·53.15·52.87dB | 20.00Mbps | 47.53dB / 0.9934 |
| C(460–470초) | 52.98dB / 0.9972 | 50.06dB | 54.44·54.48·54.42dB | 19.99Mbps | 49.27dB / 0.9953 |

- 두 회차의 출력 6개는 디코딩한 영상 프레임의 md5가 모두 같았다. 이 파일에서 VideoToolbox와 자체 디코더는 같은 결과를 냈다.
- ProRes HQ 출력은 FFmpeg 디코딩과 52.6–53.7dB(가장 낮은 프레임 50.06dB)로, FilmCraft의 H.264 디코딩·렌더링·색 변환이 정확했다. 원본이 8비트 4:2:0이라 조건이 달라서 앞 절의 55dB대와 직접 비교하지 않는다.
- 파일 중간에서 시작하는 세 구간 모두 첫 프레임부터 53dB 이상이어서, 시작 부분이 깨지지 않았다. 기준을 한 프레임 앞이나 뒤로 밀면 약 27dB로 떨어지므로, 사용자 정의 범위의 시작 프레임도 정확하다.
- 색 정보가 없는 1920×800 영상을 BT.709로 읽었다(1024×576보다 크면 BT.709, 그 이하는 BT.601: `crates/frame`의 `default_matrix`). 행렬을 다르게 읽었다면 아래 측정 함정에서 본 것처럼 약 40dB로 떨어진다.
- H.265 출력은 영상 스트림 기준 19.99–20.00Mbps로 목표를 지켰고, FFmpeg 디코딩 대비 47.5–49.7dB였다. 세 출력 모두 240개 프레임 전부 SAO가 켜져 있고 슬라이스가 1개이며(자체 인코더는 SAO가 없음), 설정 폴더 로그에 거절 기록도 없어 VideoToolbox가 만들었다.
- 내보내기 시간은 240프레임당 ProRes HQ 4.4–5.9초, H.265 1.1–1.7초였다(다른 작업과 함께 잰 값).
- 위 표는 측정 함정 두 가지를 바로잡은 뒤의 값이다. A 구간 ProRes를 처음 잰 값은 32dB였다. 첫째, FFV1/MKV 기준 파일은 시간 단위가 밀리초여서 `psnr`가 시각으로 짝지으면 세 프레임마다 이웃 프레임과 비교했다. 두 입력의 시각을 프레임 번호로 다시 쓰자(`settb=1/24,setpts=N`) 39.8dB가 됐다. 둘째, FFmpeg 9.0.2는 색 정보가 없는 기준과 BT.709로 표시된 출력을 만나면 필터 그래프에서 한쪽의 행렬을 바꿨다. 기준에도 BT.709를 붙이자 53.7dB가 나왔고, 원시 yuv420p 프레임을 직접 비교한 값(53.3dB)과 맞았다.
- 화질은 수치로만 봤고, 프레임을 원본 크기로 눈으로 비교하지는 않았다.

### H.264 부호화 기능별 읽기(합성 시험 영상) — 2026-11-17

앞 절의 배포판은 CAVLC만 쓰는 Main 프로필이고 키프레임이 모두 IDR이어서, 휴대폰·카메라 영상에 흔한 CABAC·High 프로필과 열린 GOP, SD 크기, 10비트·4:2:2, 인터레이스는 확인하지 못했다. 이번에는 FFmpeg 9.0.2의 libx264로 이런 기능을 하나씩 담은 MP4 7개(10초, 인터레이스는 5초)를 만들어, 같은 릴리스 빌드(`02cad734`)를 앞 절처럼 자동(VideoToolbox)과 `playback.hardwareDecoding=off`(자체 디코더) 두 회차로 띄워 읽었다. 영상은 `testsrc2`에 프레임마다 바뀌는 잡음을 더하고 RGB에서 정한 행렬로 변환해 CRF 18로 만들었다. 부호화 기능은 `trace_headers`로 확인했다.

파일마다 시퀀스를 만들어 전체를(a는 4–6초 범위도) Apple ProRes 422 HQ로 내보내고, FFmpeg가 같은 파일을 디코딩한 프레임과 프레임 번호로 짝지어 비교했다. 기준에는 파일을 만든 행렬을 붙였다(b·c·d는 BT.601).

| 출력 | ProRes HQ PSNR Y / SSIM Y | 가장 낮은 프레임 | 기준을 BT.709로 본 값 |
| --- | --- | --- | --- |
| a 전체(240프레임) | 51.13dB / 0.9971 | 50.74dB | – |
| a 4–6초(48프레임) | 50.90dB / 0.9970 | 50.74dB | – |
| b(250프레임) | 42.26dB / 0.9970 | 42.01dB | 22.43dB |
| c(300프레임) | 42.33dB / 0.9971 | 42.07dB | 22.43dB |
| d(240프레임) | 42.39dB / 0.9972 | 42.22dB | 22.32dB |
| f(240프레임) | 52.25dB / 0.9986 | 51.84dB | – |
| g(240프레임) | 53.98dB / 0.9986 | 53.51dB | – |

- 자동 회차에서 a 전체, b, c, d, f, g는 내보낸 프레임 수만큼 VideoToolbox가 디코딩했고(240·250·300·240·240·240프레임) 내보내는 동안 전환은 0회였다. 하드웨어 디코딩을 끈 회차에서 a·b·c·d는 모두 자체 디코더로 디코딩했고, e·f·g는 읽지 못했다. 두 회차의 a(전체·4–6초), b, c, d 출력은 디코딩한 영상 프레임의 md5가 같았다.
- 열린 GOP: a의 4–6초 범위는 IDR이 아닌 96번 I프레임에서 시작한다. 첫 프레임이 51.40dB이고 기준을 한 프레임 밀면 22.70dB로 떨어지므로, 시작 프레임이 정확하고 첫 프레임부터 깨지지 않았다. 자동 회차에서 이 범위를 내보낼 때 VideoToolbox가 `-12909`(잘못된 데이터) 오류를 내서 그 디코더는 자체 디코더로 넘어갔다. 자체 디코더가 디코딩한 51프레임은 패킷 순서와 맞는다. 범위의 48프레임에, 96번 I프레임 뒤에 디코딩하지만 앞에 표시되는 B프레임 2개(94·95번), 그리고 범위 끝 143번이 144번 I프레임 앞에 표시되는 프레임이라 먼저 디코딩해야 하는 144번 I프레임 1개를 더한 수다.
- FFmpeg 9.0.2의 VideoToolbox 디코딩도 a를 2초나 4초부터 읽으면 같은 `-12909`로 한 프레임도 내지 못했다. 0초부터 읽거나, 닫힌 GOP인 d를 4초부터 읽으면 48프레임이 소프트웨어 디코딩과 같았다. 이 Mac의 VideoToolbox가 IDR이 아닌 키프레임에서 디코딩을 시작하지 못하는 것이고, FilmCraft는 자체 디코더로 넘어가 올바른 출력을 냈다.
- 자동 회차 전체의 전환 7회 중 1회가 위 내보내기였고, 6회는 내보내기 밖에서 생겼다. 1회는 a로 시퀀스를 처음 만든 직후(자체 디코더 28프레임)였고, 5회는 b·c·f·g·e를 내보내기 전까지 사이에 한 번씩(매번 27프레임)이었으며, d로 바꿀 때는 없었다. 열린 GOP 파일은 a뿐이어서 a의 화면 표시용 디코딩으로 보이고, 27프레임은 a의 가운데인 5초(120번 프레임)를 96번 I프레임부터 디코딩한 몫(앞에 표시되는 2프레임과 96–120번 25프레임)과 맞는다. 어느 화면 요소가 디코딩했는지는 확인하지 않았다.
- 전환은 IDR이 아닌 키프레임부터 디코딩할 때 생겼다. a 전체 내보내기처럼 IDR(0번)부터 디코딩하면 VideoToolbox를 그대로 썼다(48번 앞쪽 위치를 열어도 0번부터 디코딩할 것으로 보이지만 따로 시험하지 않았다). 대신 한 번 넘어간 디코더는 하드웨어 디코더를 버리므로(`crates/platform/src/hybrid.rs`의 `fall_back`, `is_hardware`는 전환 뒤 false), 그 디코더로 나중에 IDR 위치를 열어도 자체 디코더로 디코딩한다. 속도 차이는 따로 재지 않았다.
- 색 행렬: 색 정보가 없는 SD(b·c)는 BT.601로, BT.601 행렬이 표시된 HD(d)는 표시대로 BT.601로 읽었다. 기준을 BT.601로 보면 42.3–42.4dB, BT.709로 보면 22.3–22.4dB다. ProRes 출력은 BT.709로 변환·표시되므로 측정 필터 그래프에서 한쪽의 행렬이 바뀐다. 42dB대는 이 측정의 한계다. FFmpeg가 b를 직접 BT.709 10비트 4:2:2로 바꾼 결과(`accurate_rnd`, 색차 전체 보간)는 같은 측정에서 41.23dB로 FilmCraft(42.26dB)보다 낮았다. RGB로 바꿔 비교한 평균 PSNR(색차 보간 차이로 값 자체는 낮다)도 d(BT.601) 35.47dB, a(BT.709) 35.42dB로 같은 수준이었다. SD인 b는 RGB에서 32.35dB로 HD보다 낮지만, FFmpeg가 직접 변환한 결과도 같은 측정에서 29.34dB여서 FilmCraft만의 손실은 아니다. FFmpeg 변환과의 비교는 b에서만 했다.
- 10비트·4:2:2: 이 M1의 VideoToolbox는 High 10과 High 4:2:2를 하드웨어로 디코딩했다(52.25·53.98dB). 자체 디코더는 8비트 4:2:0 프로그레시브만 지원하므로(`crates/h264`의 `check_supported`), 하드웨어 디코딩을 끄면 두 파일 모두 읽지 못했다(로그 `bit depth luma 10 chroma 10 (only 8-bit is implemented)`, `chroma_format_idc 2 (only 4:2:0 is implemented)`). VideoToolbox 세션은 하드웨어 디코딩을 요구하도록 열리므로(`crates/platform/src/videotoolbox.rs`), 하드웨어가 이 형식을 받지 않는 장비에서는 읽을 경로가 없다.
- 인터레이스: VideoToolbox 경로는 거절했고(`declined` 1회. 거절 이유는 코드상 `field-coded H.264`이며 로그에는 남지 않는다: `crates/platform/src/videotoolbox.rs`의 `layout`), 자체 디코더도 지원하지 않아 로그에 `media unreadable: …: H.264: interlaced (field / MBAFF) coding`이 남았다. 가져오기는 오류 없이 끝났고(`errors: []`) 내보내기 화면(`ui.inspect`·`ui.elements`)에도 경고가 없었다. 내보내기는 "Done"으로 끝났지만 150프레임 전부 "MEDIA UNREADABLE" 안내 화면이었다(모든 프레임의 밝기 평균이 같고, 프로그램 모니터에도 같은 화면이 보였다). 하드웨어 디코딩을 끈 회차의 f·g 출력도 같은 안내 화면이었다. 안내 화면의 "File > Link Media… reconnects it" 문구는 지원하지 않는 형식에도 나온다(`crates/render/src/offline.rs`).
- 내보내기 시간은 읽은 파일 기준 1080p 240프레임 ProRes HQ 7.2–9.8초, SD 1.3–1.8초였다(다른 작업과 함께 잰 값).
- 시험 영상은 합성이어서 실제 카메라·휴대폰 인코더의 출력과 다를 수 있다. 화질은 수치로만 봤다.

## 재현

`filmcraft` 디렉터리에서 실행한다. 출력 폴더는 소스 저장소 밖의 절대 경로를 지정한다.

```sh
FILMCRAFT_REQUIRE_ORACLES=1 cargo test --locked --release -p filmcraft-hevcenc
FILMCRAFT_REQUIRE_ORACLES=1 cargo test --locked --release -p filmcraft-hevc --test it
FILMCRAFT_DELIVERY_DIR=/absolute/quality FILMCRAFT_REQUIRE_ORACLES=1 cargo test --locked --release -p filmcraft-hevcenc --test delivery_quality -- --ignored --nocapture
FILMCRAFT_DELIVERY_DIR=/absolute/delivery FILMCRAFT_REQUIRE_ORACLES=1 cargo test --locked --release -p filmcraft-platform --test hevc_delivery_validation -- --ignored --nocapture --test-threads=1
FILMCRAFT_REQUIRE_ORACLES=1 cargo test --locked --release -p filmcraft-platform --test videotoolbox_hevc_hdr_export -- --test-threads=1
cargo test --locked --release -p filmcraft-hevcenc --test perf -- --ignored --nocapture
```

`delivery_quality`는 원본·reconstruction·Annex-B와 PSNR/비트레이트 CSV를 남긴다. 외부 도구로 reconstruction과 디코딩 결과를 대조하고 원본과 SSIM을 추가 측정할 수 있다. 긴 검사는 비용·파일 출력을 명시하도록 ignored지만 이번에는 `--ignored`로 본문을 실행했다.

### 데스크톱 앱 내보내기

빈 설정 폴더와 새 토큰으로 앱을 띄운다. 토큰은 [control-protocol.md](control-protocol.md)대로 환경 변수로만 넘기고 출력하지 않는다.

```sh
cargo build --release --locked -p filmcraft
export FILMCRAFT_CONTROL_TOKEN="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"
FILMCRAFT_DATA_DIR=/absolute/empty-profile target/release/filmcraft --control 9877
```

`127.0.0.1:9877`에 JSON 한 줄 요청(`token` 포함)을 보내 다음 순서로 조작했다. 새 설정 폴더에서는 업데이트 안내 창이 먼저 떠서 Later를 눌러 닫았다(1440×817 창에서 `ui.click {x: 789, y: 458.6}`).

1. `ui.click {id: "header.mode.export"}`로 내보내기 화면을 연다.
2. `export.format`을 누르고 `export.format.option.1`(H.265 (HEVC))을 고른다.
3. 글자 칸(`export.location`, `export.fileName`, `export.video.width`·`export.video.height`, `export.range.start`·`export.range.end`)은 칸을 누른 뒤 `ui.key {key: "Cmd+A"}`, `ui.type {text}`, `ui.key {key: "Enter"}` 순서로 바꾼다. 칸을 누르지 않고 키를 보내면 앱 단축키로 처리된다(Enter는 미리보기 렌더링을 시작함).
4. 프레임 크기는 `export.video.matchSize`를 꺼서 바꾼다. 범위는 `export.range`에서 `export.range.option.3`(사용자 정의)을 고른다.
5. 자체 인코더를 쓰려면 `export.video.aspect`에서 `export.video.aspect.option.3`(HD Anamorphic 1080)을 고른다.
6. HDR은 `ui.menu.invoke {command: "sequence.colorSettings"}`로 색 관리 창을 열고 `colorDialog.working.rec2100-pq`나 `colorDialog.working.rec2100-hlg`, `colorDialog.ok`를 누른다.
7. `ui.click {id: "export.button"}`으로 내보내고, `engine.execute {command: "jobs.list"}`로 끝날 때까지 기다린다.

어느 인코더가 썼는지는 `<설정 폴더>/Logs/filmcraft.log`의 `hardware HEVC encoding declined` 줄과 비트스트림 헤더로 확인했다.

```sh
ffprobe -v error -show_streams -show_format out.mp4
ffmpeg -v error -i out.mp4 -f null -
ffmpeg -v trace -i out.mp4 -map 0:v -c copy -bsf:v trace_headers -f null - 2>&1 \
  | grep -E 'sample_adaptive_offset_enabled_flag|pps_deblocking_filter_disabled_flag|first_slice_segment_in_pic_flag'
```

AVFoundation 검사는 `AVURLAsset`의 `isPlayable`·`containsHDRVideo` 특성과 `AVAssetReader`로 모든 영상 프레임을 읽는 짧은 Swift 프로그램으로 했다(저장소에는 넣지 않음).

#### 복잡한 4K 영상의 비트레이트·화질

시험 영상은 `filmcraft` 디렉터리의 `target/fixtures/`에 만든다(강한 잡음은 `alls=40`, 파일 이름 `heavy709-4k.mov`). `testsrc2`는 `duration=5`에서 120프레임을 내므로 `-frames:v 119`로 119프레임에 고정한다. `noise` 필터의 기본 시드는 고정이어서 같은 명령은 같은 영상을 만든다(다시 만든 영상과 앞서 측정한 H.265 파일의 PSNR이 소수점 여섯째 자리까지 같았다).

색 행렬을 BT.709로 변환하고 `-colorspace bt709`를 붙여야 FilmCraft가 같은 행렬로 읽는다. 이 MOV에는 행렬(`colorspace`)과 범위만 기록되고, 원색·전송 특성은 `-color_primaries`·`-color_trc`(`-movflags +write_colr` 포함)를 붙여도 기록되지 않았다. 측정에 쓴 영상도 같았고, FilmCraft는 둘 다 BT.709로 읽는다.

```sh
mkdir -p target/fixtures
ffmpeg -f lavfi -i "testsrc2=size=3840x2160:rate=24000/1001:duration=5,noise=alls=12:allf=t+u,scale=out_color_matrix=bt709:out_range=tv,format=yuv422p10le" \
  -f lavfi -i "sine=frequency=440:sample_rate=48000:duration=5" \
  -frames:v 119 -c:v prores_ks -profile:v 2 -colorspace bt709 -color_range tv \
  -c:a pcm_s24le target/fixtures/grain709-4k.mov
```

앱에서는 다음 순서로 내보냈다.

1. `engine.execute {command: "file.import", params: {paths: ["/absolute/target/fixtures/grain709-4k.mov"]}}`로 가져오고, 돌려받은 항목 ID로 `file.newSequenceFromClip {items: [id]}`를 실행한다. 새 시퀀스가 활성 시퀀스가 된다. 내보내기 화면이 이미 열려 있었다면 `header.mode.edit`, `header.mode.export`를 차례로 눌러 새 시퀀스를 대상으로 바꾼다.
2. 위 순서대로 H.265를 고르고 기본 설정(VBR 1패스, 목표 20Mbps·최대 30Mbps)으로 내보낸다.
3. 50Mbps는 `export.video.max`에 75, `export.video.target`에 50을 글자 칸 방식(칸 누르기, `Cmd+A`, 입력, `Enter`)으로 넣고 내보낸다. 측정 때는 최대를 먼저 75로 바꾼 뒤 목표를 50으로 바꿨다.

앱은 회차마다 빈 설정 폴더로 띄운다([데스크톱 앱 내보내기](#데스크톱-앱-내보내기) 참고).

1. 자체 디코더 회차에서는 가져오기 전에 `engine.execute {command: "prefs.set", params: {key: "playback.hardwareDecoding", value: "off"}}`를 실행한다. VideoToolbox 회차는 기본값(`auto`) 그대로 둔다.
2. `engine.execute {command: "file.import", params: {paths: ["/absolute/tos1080/tears_of_steel_1080p.mov"]}}`로 가져오고, 돌려받은 항목 ID로 `file.newSequenceFromClip {items: [id]}`를 실행한 뒤 `header.mode.export`를 눌러 내보내기 화면을 연다. 내보내기 화면이 이미 열려 있었다면 `header.mode.edit`, `header.mode.export`를 차례로 눌러 새 시퀀스를 대상으로 바꾼다.
3. `export.range`에서 `export.range.option.3`(사용자 정의)을 고르고, `export.range.start`·`export.range.end`에 초 단위로 190·200(A), 280·290(B), 460·470(C)을 글자 칸 방식으로 넣는다.
4. 구간마다 Apple ProRes(422 HQ)와 H.265 기본 설정으로 `target/fixtures/`에 내보낸다. 두 회차의 출력이 겹치지 않도록, VideoToolbox 회차는 `hw-pr-a`·`hw-vt-a`, 자체 디코더 회차는 `sw-pr-a`·`sw-vt-a`처럼 회차 접두어를 붙인다.
5. `engine.execute {command: "perf.stats"}`의 `result.decode.hardware`에서 `frames`(VideoToolbox)와 `softwareFrames`(자체 디코더)를 확인한다.

측정은 두 입력의 시각을 프레임 번호로 다시 쓰고, 색 정보가 없는 기준에 BT.709·제한 범위를 붙여서 한다. 두 회차의 출력이 같은지는 디코딩한 영상 프레임의 md5로 비교한다. H.265를 만든 인코더는 위 [데스크톱 앱 내보내기](#데스크톱-앱-내보내기)의 `trace_headers` 명령으로 확인한다.

```sh
for n in a b c; do
  for out in "target/fixtures/hw-pr-$n.mov" "target/fixtures/hw-vt-$n.mp4"; do
    ffmpeg -i "$out" -i "target/fixtures/tos1080-ref-$n.mkv" -lavfi \
      "[0:v]settb=1/24,setpts=N,format=yuv420p,split[a1][a2];[1:v]setparams=colorspace=bt709:color_primaries=bt709:color_trc=bt709:range=tv,settb=1/24,setpts=N,format=yuv420p,split[b1][b2];[a1][b1]psnr=stats_file=target/fixtures/psnr-${out##*/}.log;[a2][b2]ssim" \
      -f null -
  done
  for f in "pr-$n.mov" "vt-$n.mp4"; do
    hw=$(ffmpeg -v error -i "target/fixtures/hw-$f" -map 0:v -f md5 -)
    sw=$(ffmpeg -v error -i "target/fixtures/sw-$f" -map 0:v -f md5 -)
    [ "$hw" = "$sw" ] && echo "$f: identical" || echo "$f: DIFFERENT"
  done
done
```

#### H.264 부호화 기능별 읽기

시험 영상은 `target/fixtures/h264/`에 만든다. 이 절의 명령 블록은 한 셸에서 차례로 실행한다(뒤 블록이 앞 블록의 `d`·`t709`·`t601`과 `m`을 쓴다). 변수(`$gop` 등)는 늘 따옴표로 묶어 한 인자로만 넘기고 여러 옵션을 한 변수에 넣어 펼치지 않으며, 프로세스 치환도 쓰지 않아 sh·bash·zsh에서 똑같이 동작한다.

```sh
d=target/fixtures/h264; mkdir -p "$d"
src() { echo "testsrc2=s=${1}:r=${2}:d=${3},format=gbrp,noise=alls=8:allf=t+u,scale=out_color_matrix=${4}:out_range=tv,format=${5}"; }
t709="setparams=colorspace=bt709:color_primaries=bt709:color_trc=bt709:range=tv"
t601="setparams=colorspace=smpte170m:color_primaries=bt709:color_trc=bt709:range=tv"
none="setparams=colorspace=unknown:color_primaries=unknown:color_trc=unknown:range=tv"
gop="keyint=48:min-keyint=48:scenecut=0:bframes=3:b-pyramid=normal:ref=4:weightp=2"
enc() { out=$1; shift; ffmpeg -nostdin -y -v error "$@" -c:v libx264 -preset medium -crf 18 -an -movflags +faststart "$d/$out"; }
enc a-high-opengop.mp4 -f lavfi -i "$(src 1920x1080 24 10 bt709 yuv420p),$t709" -profile:v high -x264-params "$gop:open-gop=1"
enc b-sd576-untagged.mp4 -f lavfi -i "$(src 720x576 25 10 bt601 yuv420p),$none" -profile:v high -x264-params "keyint=50:min-keyint=50:scenecut=0"
enc c-sd480-untagged.mp4 -f lavfi -i "$(src 720x480 30000/1001 10 bt601 yuv420p),$none" -profile:v high -x264-params "keyint=60:min-keyint=60:scenecut=0"
enc d-hd-601-tagged.mp4 -f lavfi -i "$(src 1920x1080 24 10 bt601 yuv420p),$t601" -profile:v high -x264-params "$gop"
enc e-1080i-mbaff.mp4 -f lavfi -i "$(src 1920x1080 30000/1001 5 bt709 yuv420p),$t709" -profile:v high -flags +ildct+ilme -x264-params "interlaced=1:tff=1:keyint=30"
enc f-high10.mp4 -f lavfi -i "$(src 1920x1080 24 10 bt709 yuv420p10le),$t709" -profile:v high10 -x264-params "$gop"
```

부호화 기능은 첫 프레임의 매개변수 집합으로 확인하고, a의 열린 GOP는 I프레임 수와 IDR 수로 확인한다(`trace_headers`는 `-v verbose` 이상에서만 출력한다).

```sh
for f in "$d"/*.mp4; do
  echo "$f"
  ffmpeg -nostdin -v verbose -i "$f" -frames:v 1 -c copy -bsf:v trace_headers -f null - 2>&1 \
    | grep -oE '(profile_idc|entropy_coding_mode_flag|transform_8x8_mode_flag|frame_mbs_only_flag|mb_adaptive_frame_field_flag|chroma_format_idc|bit_depth_luma_minus8|matrix_coefficients|weighted_pred_flag) +[01]+ += +[0-9]+' \
    | sort -u
done
ffprobe -v error -select_streams v:0 -show_entries frame=pict_type -of csv=p=0 "$d/a-high-opengop.mp4" | grep -c '^I'
ffmpeg -nostdin -v error -i "$d/a-high-opengop.mp4" -c copy -bsf:v filter_units=pass_types=5 -f framecrc - | grep -vc '^#'
```

앱은 회차마다 빈 설정 폴더로 띄운다([데스크톱 앱 내보내기](#데스크톱-앱-내보내기) 참고). 업데이트 안내 창은 제어 포트가 열린 뒤 몇 초 늦게 뜰 수 있다. Later를 누른 뒤(1440×816 창에서 `ui.click {x: 789.6, y: 458.4}`) 내보내기 화면을 열었을 때 `ui.inspect`의 `result.ui.export.forSequence`가 `null`이 아닌지 확인한다.

1. 자체 디코더 회차에서는 가져오기 전에 `engine.execute {command: "prefs.set", params: {key: "playback.hardwareDecoding", value: "off"}}`를 실행한다.
2. 파일마다 `file.import`로 가져오고, 돌려받은 항목 ID로 `file.newSequenceFromClip {items: [id]}`를 실행한 뒤 `header.mode.edit`, `header.mode.export`를 차례로 누른다. `export.location`은 `target/fixtures/h264`의 절대 경로, 형식은 `export.format.option.3`(Apple ProRes, 기본 422 HQ)이다. 표시 지점이 없는 새 시퀀스의 범위는 전체(`entire`)다.
3. 파일 이름에는 회차 접두어를 붙인다(`hw-a`·`sw-a`, b–g도 같은 방식). a는 `export.range.option.3`(사용자 정의)을 고르고 4·6초를 넣어 `hw-a-mid`·`sw-a-mid`로 한 번 더 내보낸다.
4. 내보내기 전후로 `perf.stats`의 `result.decode.hardware`(`frames`, `softwareFrames`, `fallbacks`, `declined`)를 기록한다. 전환·거절 이유는 `<설정 폴더>/Logs/filmcraft.log`의 `VideoToolbox H.264 failed`, `media unreadable` 줄로 본다.

측정은 다음과 같다. `m`의 인자는 출력, 원본, 기준에 붙일 색 정보, 비교 형식, 로그 이름, 원본 자르기(선택)다.

```sh
m() {
  ffmpeg -nostdin -i "$d/$1" -i "$d/$2" -lavfi \
    "[0:v]settb=1/1000,setpts=N,format=$4,split[a1][a2];[1:v]${6:+$6,}$3,settb=1/1000,setpts=N,format=$4,split[b1][b2];[a1][b1]psnr=stats_file=$d/psnr-$5.log;[a2][b2]ssim" \
    -f null - 2>&1 | grep -E 'Parsed_(psnr|ssim)'
}
m hw-a.mov a-high-opengop.mp4 "$t709" yuv420p hw-a
m hw-a-mid.mov a-high-opengop.mp4 "$t709" yuv420p hw-a-mid "trim=start_frame=96:end_frame=144,setpts=PTS-STARTPTS"
m hw-a-mid.mov a-high-opengop.mp4 "$t709" yuv420p hw-a-mid-shift "trim=start_frame=97:end_frame=145,setpts=PTS-STARTPTS"
for n in b-sd576-untagged c-sd480-untagged d-hd-601-tagged; do
  x=${n%%-*}
  m "hw-$x.mov" "$n.mp4" "$t601" yuv420p "hw-$x-601"
  m "hw-$x.mov" "$n.mp4" "$t709" yuv420p "hw-$x-709"
done
m hw-f.mov f-high10.mp4 "$t709" yuv420p10le hw-f
m hw-g.mov g-high422-10.mp4 "$t709" yuv422p10le hw-g
for x in a a-mid b c d; do
  hw=$(ffmpeg -nostdin -v error -i "$d/hw-$x.mov" -map 0:v -f md5 -)
  sw=$(ffmpeg -nostdin -v error -i "$d/sw-$x.mov" -map 0:v -f md5 -)
  [ "$hw" = "$sw" ] && echo "$x: identical" || echo "$x: DIFFERENT"
done
for x in hw-e sw-e sw-f sw-g; do
  printf '%s: ' "$x"
  ffmpeg -nostdin -v error -i "$d/$x.mov" -vf "signalstats,metadata=print:key=lavfi.signalstats.YAVG:file=-" -f null - \
    | grep -oE 'YAVG=[0-9.]+' | sort | uniq -c
done
```

FFmpeg의 VideoToolbox가 열린 GOP의 중간 키프레임에서 시작하지 못하는 것과, SD의 42dB대가 측정 한계라는 것은 다음으로 확인했다.

```sh
for t in a-high-opengop.mp4:0 a-high-opengop.mp4:2 a-high-opengop.mp4:4 d-hd-601-tagged.mp4:4; do
  f=${t%%:*}; s=${t##*:}; rm -f "$d/vt.md5" "$d/sw.md5"
  e=$(ffmpeg -nostdin -y -v warning -hwaccel videotoolbox -ss "$s" -i "$d/$f" -frames:v 48 -pix_fmt yuv420p -f framemd5 "$d/vt.md5" 2>&1 | grep -c -- '-12909')
  ffmpeg -nostdin -y -v error -ss "$s" -i "$d/$f" -frames:v 48 -f framemd5 "$d/sw.md5"
  grep -v '^#' "$d/vt.md5" 2>/dev/null | awk -F, '{print $NF}' > "$d/vt.sum"
  grep -v '^#' "$d/sw.md5" | awk -F, '{print $NF}' > "$d/sw.sum"
  n=$(wc -l < "$d/vt.sum" | tr -d ' ')
  if [ "$n" -gt 0 ] && cmp -s "$d/vt.sum" "$d/sw.sum"; then r="same as software"; else r="not the same"; fi
  echo "$f from ${s}s: VideoToolbox $n frames, $r, -12909 lines $e"
done
ffmpeg -nostdin -y -v error -i "$d/b-sd576-untagged.mp4" \
  -vf "scale=in_color_matrix=bt601:out_color_matrix=bt709:in_range=tv:out_range=tv:flags=accurate_rnd+full_chroma_int+full_chroma_inp,format=yuv422p10le,$t709" \
  -c:v ffv1 "$d/b-ffmpeg709.mkv"
m b-ffmpeg709.mkv b-sd576-untagged.mp4 "$t601" yuv420p ffmpeg-b-601

}
rgb hw-a.mov a-high-opengop.mp4 "$t709"
rgb hw-d.mov d-hd-601-tagged.mp4 "$t601"

```

## 남은 한계

- 소프트웨어 출력은 4:2:0 8/10비트다. 4:2:2 확장은 입력 디코더이며 4:2:2 출력으로 안내하지 않는다.
- B프레임·디블로킹·SAO·RDOQ·2패스·CRF 등은 미지원이다.
- Windows/NVIDIA·Linux 실기, 실사 다종 코퍼스, 장편 8K 메모리/안정성은 미검증이다.
- 인코딩 중간 GPU/드라이버 장애 복구는 미검증이며 초기화 실패 fallback과 구분한다.
- 앱 내보내기의 실사 확인은 이미 압축된 배포판(Tears of Steel)으로만 했다. 4K판은 FFmpeg로 ProRes로 옮긴 10초 구간 3개로, 1080p판은 H.264를 그대로 읽은 10초 구간 3개로 했다. 카메라 RAW·로그 촬영본, HDR 실사, 8K·HDR 출력의 원본 크기 화질은 미검증이다.
- H.264 직접 읽기는 실사 배포판 하나(CAVLC Main, 키프레임이 모두 IDR)와 libx264로 만든 합성 시험 영상 7개로 확인했다. 실제 카메라·휴대폰 인코더의 출력, 필드 픽처(PAFF) 인터레이스, High 4:4:4, 비정사각 픽셀 SD, BT.709가 아닌 원색·전송 특성(BT.2020 등)은 미검증이다. 4K판처럼 구간 중간부터 디코딩하면 FFmpeg가 참조 프레임 경고를 내는 원본도 FilmCraft로 직접 읽지 않았다.
- H.264 인터레이스는 두 디코더 모두 읽지 못하고, 10비트·4:2:2 H.264는 자체 디코더가 읽지 못해 하드웨어 디코더로만 읽는다(이 Mac에서는 VideoToolbox. 다른 플랫폼의 하드웨어 디코더는 미검증). 읽지 못하는 미디어가 든 시퀀스도 내보내기가 경고 없이 "Done"으로 끝나고 출력에는 안내 화면이 들어간다.
- 열린 GOP H.264를 IDR이 아닌 키프레임부터 디코딩하면 VideoToolbox가 실패해 그 디코더는 자체 디코더로 넘어가고, 그 디코더는 이후에도 자체 디코더로 디코딩한다. 그 범위의 출력은 자체 디코더로 올바르게 나왔지만, 속도 영향은 재지 않았다.
- 이 Mac에서 정사각 픽셀·짝수 크기의 기본 설정(VBR 1패스) H.265는 SDR·HDR 모두 VideoToolbox로 간다. 앱에서 자체 인코더는 비정사각 픽셀로 VideoToolbox가 거절하게 한 1440×1080 출력 2개로만 확인했다.
- 앱 시험은 로컬 릴리스 프로필 빌드로 했다. 배포용 릴리스 패키지(craft-fonts 포함·서명)는 시험하지 않았다.
- 위 성능·품질 수치를 모든 장비·콘텐츠의 결과로 일반화하지 않는다.
